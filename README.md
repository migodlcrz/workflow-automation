# SupportOps Automation

An AI-powered internal support ticket platform that automates the full lifecycle from submission to resolution. Users submit tickets through a web form, Groq LLM triages and routes them automatically, and support agents manage everything from a centralized dashboard — with all data synced to Google Sheets in real time.

---

## What It Does

1. **User submits a ticket** via a validated form (`/submit`)
2. **Server Action** validates input with Zod and saves to Supabase
3. **Groq AI** triages the ticket: assigns category, priority, team, confidence score, tags, estimated resolution time, and root cause
4. **AI metadata** is written back to the same ticket row in Supabase
5. **Google Sheets** row is created/updated for stakeholder visibility
6. **Support agents** manage tickets via the dashboard (`/support`) with search, filter, and status controls

Ticket submission succeeds even if AI triage or Sheets sync fails — those are non-blocking.

## Architecture

```
Browser (React)
    │
    ▼
Server Actions  (/src/app/actions/tickets.ts)
    │
    ├──▶ Supabase (insert ticket)
    │
    ├──▶ Groq AI Service  (/src/services/ai/triage.ts)
    │         └──▶ Supabase (update ticket with AI metadata)
    │
    ├──▶ Google Sheets Service  (/src/services/google-sheets/sync.ts)
    │
    └──▶ revalidatePath() (invalidate dashboard cache)
```

There are no custom API routes. All mutations go through Next.js Server Actions. Read queries run directly in async Server Components using helpers in `/src/lib/supabase/queries.ts`.

## Data Model

Single `tickets` table in Supabase:

```
id                      UUID (PK)
ticket_number           "SUP-20260609-0001" (auto-generated by trigger)

full_name               string
email                   string
department              enum (IT | HR | Finance | Operations | Sales | Marketing | Legal | Engineering | Product | Other)

subject                 string
description             string
urgency_level           enum (low | medium | high | critical)
affected_system         string?
attachment_url          URL?

status                  enum (open | in_progress | resolved | closed)

ai_category             string  (Hardware | Software | Network | Access & Permissions | ...)
ai_priority             enum (low | medium | high | critical)
ai_summary              string
ai_suggested_team       string
ai_confidence_score     float (0.0–1.0)
ai_tags                 string[]
ai_estimated_resolution string ("2–4 hours")
ai_root_cause           string
ai_analysis_raw         JSONB
ai_analyzed_at          timestamp

sheets_synced_at        timestamp?
created_at              timestamp
updated_at              timestamp  (auto-updated by trigger)
```

Indexed on: `status`, `created_at`, `email`, `department`, `ai_priority`.

## Environment Variables

Create a `.env.local` file (see `.env.example`):

```env
# Supabase
NEXT_PUBLIC_SUPABASE_URL=
NEXT_PUBLIC_SUPABASE_ANON_KEY=
SUPABASE_SERVICE_ROLE_KEY=

# Groq AI
GROQ_API_KEY=
GROQ_MODEL=llama-3.3-70b-versatile

# Google Sheets (service account)
GOOGLE_SERVICE_ACCOUNT_EMAIL=
GOOGLE_PRIVATE_KEY=
GOOGLE_SHEETS_SPREADSHEET_ID=
GOOGLE_SHEETS_TAB_NAME=Tickets
```

`NEXT_PUBLIC_*` variables are exposed to the browser. All others are server-side only.

## Getting Started

**Prerequisites:** Node.js 18+, a Supabase project, a Groq API key, a Google Cloud service account with the Sheets API enabled.

```bash
# Install dependencies
npm install

# Run the development server
npm run dev
# → http://localhost:3000

# Build for production
npm run build
npm start

# Lint
npm run lint
```

**Database setup:** Run `supabase/schema.sql` against your Supabase project to create the `tickets` table, triggers, RLS policies, and indexes.

**Google Sheets setup:** Share the target spreadsheet with the service account email (Editor permission). The sync service will create the header row on first run.

## Key Design Decisions

**Server Actions over API routes** — form mutations call server functions directly, eliminating the need for a separate API layer and reducing client/server round-trips.

**Non-blocking AI and Sheets** — AI triage and Sheets sync run after the ticket is saved. If they fail, the ticket is still created and the user sees a success page. This keeps the submission path reliable.

**Single-table design** — all ticket data and AI metadata live in one row. No joins required for any query in the dashboard or analytics pages.

**`force-dynamic` on dashboard pages** — the support dashboard and analytics page opt out of static generation so they always reflect current data without manual cache invalidation.

**AI confidence fallback** — if Groq returns malformed JSON or times out, the triage service falls back to `category: "General IT"`, `priority: "medium"`, `confidence: 0`. The ticket is never left in a broken state.
